Decided: Backlog is deleted, and this is where its four groups go

Backlog and Tickets were the same list read twice — the drift the shared watchLabels function exists to prevent, one level up. Everything Backlog did lands here or it is a capability lost silently, so each of its parts is named:

Backlog hadBecomesWhy that shape
Four groups — Watched, Blocked at intake, Unwatched, Ignored the Watch filter's four values, plus the intake call-out above the list one pass, one assignment per item — the property groups had, kept: an item matching two predicates would draw twice with two switches, and the second is a different answer to the same question
Intake pulled out, not greyed inside Watched a call-out with a count and a Show them filter, and a lamp on the row an unclear assay is the one intake reading that stops dispatch; among 96 rows it reads as a detail rather than as the thing holding all the work
Override → workable on intake rows the same button, same setIssueAssay call, on the same rows the second and last thing on a row that writes. On intake rows alone: a workable verdict blocks nothing, so the button on one would offer to change a reading that changes no behaviour
The assayer's sentence, quoted the row's subline, quoted whole it is the only account of why the goal is held, so a paraphrase would be the only account there is, and wrong
Features as headings, folds on Place.collapsed group=feature — the same groupByFeature, the same collapsed field, the same container controls on the heading a container is never dispatched at, so it is never a row. group=flat brings back the Feature column, which is what a GitHub world with no hierarchy gets — and groupByFeature returning null already means “draw the flat list”
The name opens the goal page unchanged — selectGoal, from the name, refs beside it one way into a goal from every surface that lists one; a reference never goes inside a button, because one click cannot have two destinations
25 rows then “and 31 more” the keyset cursor and infinite scroll this tab already has the cut existed because the backlog drew from the snapshot; a paged list does not need it
The nav badge — unwatched count, read off backlogGroups the same number on the Tickets button, read off the mirror's watch filter TopBar.tsx:42 is the one consumer outside the tab, and deleting Backlog.tsx without moving it takes the only number that says whether triage is worth opening

What is actually deleted

  • web/src/console/Backlog.tsx, and 'backlog' from ConsoleTab and from TABS in place.ts — the second is the site nothing checks.
  • ?tab=backlog resolves to the tickets tab rather than 404ing to the overview. place.ts already falls back to overview for an unknown tab, which would silently strand every bookmark and shared link an operator has. One alias entry, and a line in the spec's address-bar table saying it is one.
  • Nothing under web/src/ that Backlog owned may simply stop being imported. backlogGroups moves to the panel (or dies with its last caller); watchBucket, groupByFeature, groupProgress and isContainerType keep their callers here. knip runs with every rule at error, so an export left behind turns npm run check red — which is the good case. The bad case is deleting a helper the merged panel needed and rewriting it slightly differently.
  • The spec's whole ## The backlog section is rewritten into the tickets section in the same change, not deleted: the arguments in it — one assignment per item, intake pulled out, containers as headings, the quote-never-parse rule, features open until folded — are the reasons this design is shaped the way it is, and they outlive the tab they were written for.

1 · Every screen reads the mirror; the mirror is rewritten each pulse

  • A pulse writes what it saw. One sweep per pulse over the assignment filter, upserting by number — the same call the snapshot already makes, so no new provider traffic on the common path.
  • Closed means stop tracking, not delete. A row whose state left the open set is marked tracking='frozen' and the sweep skips it. It keeps its last-read title, labels, state and parent. Deleting it would take the cost history and the verdict with it, and the close-out sweep recognises its own obligation by finding the item again.
  • Thaw is one condition, not a judgement: the tracker returns it in the open set again.
  • The dispatcher does not read this table, and must not start. Rules keep deciding from the live snapshot — a rule that could see a frozen row would eventually dispatch onto a closed item, and nothing would look wrong.

2 · The table is a control now — two of them

The shipped tab states “nothing in it is a control that changes the world — a history you can edit from is not a history.” That sentence was true of a record and is false of this surface, so it changes in docs/spec/17-cockpit.md in the same commit as the code.

  • Two controls, and no more: the watch switch and the intake override. Both already exist and both keep their routes — POST /api/issues/:number/watch and setIssueAssay — so the merged surface introduces no new way to change the world.
  • Only on live rows. A frozen row's switch is inert with a title saying why: there is nothing in the tracker left to tag.
  • A container cascades, and the heading says so before the click — and a partial failure is reported (“tagged 6 of 9”), because an operator told “watched” while three children kept the old tag has been lied to about what the harness will pick up.
  • Optimistic, then reconciled by the pulse. Trusting the click alone would leave the tab claiming a tag the tracker refused.
  • A gate-off deployment (labelPrefix: '') refuses both directions and says why — there is no tag to write, and a button that writes nothing is worse than one that explains itself.

3 · “Why is nothing on this?” — quoted, never re-derived

isIssuePickupEligible already returns {eligible, reasons[]}, and the funnel's route says the rest. The tooltip ships those strings. A lens that reasoned about pickup would be a second dispatcher, and the two would drift the first time a gate changed.

  • Only where the question makes sense — a live row that is watched with no agent and no PR. A frozen row has no reasons, because eligibility is a reading of the live world.
  • Quiet marker on a feature heading: a container is never worked itself, which is an explanation rather than a problem.
  • Reasons it can carry today, verbatim from the gates: tagged leave-alone; no watch tag; the watch tag was added by someone else; a container type; a state outside pickupStates; assay unclear; plan awaiting approval; blocked on a human part; attempt cap reached.
  • Hover is not the only way to it — the same list is the row's expanded panel on click. A tooltip nobody can select text out of is where a stack trace goes to die.

4 · Parent feature, and the colour

Issue.parent has three distinct values and the surface must keep them apart — grouped as headings, or flat as a column.

ValueMeansDrawn
a parentthe Feature this hangs offcoloured heading / chip
nullan orphan — genuinely no parenthatched “no feature” heading
undefinedthe link could not be read, or no hierarchy“parent unreadable”, kept out of the orphan group

Folding unreadable into orphan would say this item belongs to no feature, which is a different and wrong thing to say about a link we could not fetch. The provider is already careful about exactly this; the surface must not undo it.

On “a random colour persisted in the db”

  • Persisted: yes. The whole value is that the same feature is the same colour every morning. One row per feature id, written on first sight.
  • Random: recommend not. A random hue has two failures with nothing to catch them — one that vanishes against --panel-2, and two features that land near-identical. Instead a fixed twelve-hue ladder at one lightness and chroma, assigned next-least-used at first sight, then persisted. Past twelve the ladder repeats, which is honest: a legend with forty colours is not a legend anyone reads.
  • Colour is never the only signal — number and name ride on every heading and chip, so the column works for a colour-blind reader and in a screenshot pasted into a ticket.

5 · States: the tracker's own words, on the deployments that have them

  • Two tiers, not one control. Tracking (live / frozen) is the harness's reading; State is the tracker's own word. Folding them would state a triage nobody made — Removed and Closed are both frozen and are not the same fact.
  • The state list is discovered, never hardcoded — the distinct set the mirror has seen, with counts. A hardcoded Azure ladder is wrong on the first customised process template, and silently: the missing state's items stop being reachable by any filter.
  • GitHub and the fake have no native states, so the second tier is not drawn and the coarse axis reads Open / Closed. A filter offering states the provider cannot produce is a control that always returns nothing.
  • The ▲ marks a state pickupStates lets through, read from config — the most-asked question about an Azure deployment, answered where the states are.

Where the pieces go

  • Store: src/store/tickets.ts keeps the table. New columns on an existing table — tracking, work_item_state, parent_number, parent_title, last_read_at — each need an additive ALTER TABLE in that module's ColumnMigrations, or they are invisible on every database from before today with nothing erroring. The feature-colour table is a fresh CREATE TABLE that declares an empty column list anyway.
  • Sweep: the pulse's mirror write gains the freeze rule and the parent columns. Still a record — nothing under src/dispatcher/ reads it, and that belongs in a structural test, not a comment.
  • Route: GET /api/tickets grows tracking, a provider-native state, feature and group; the response ships the discovered state list with counts, the feature legend with colours, the intake count, and per-row reasons. Wrapped in checked(...). No new write route — both controls already have one.
  • Wire: TicketRow gains workItemState, tracking, parent, featureColor, pickupReasons, assay.
  • Place: tracking, state, feature, group join the tab's three fields; collapsed is inherited from the backlog, and backlog leaves TABS with an alias behind it.
  • Panel: TicketsPanel.tsx absorbs Backlog.tsx, which is deleted.
  • Specs, same change: 17-cockpit.md (the merged tab, the deleted section, the “no controls” sentence, the nav, the address bar), 16-http-api.md, 14-persistence.md, 15-integrations.md, 06-issue-pickup.md.

Still open

  • Sequencing. This is comfortably four changes: the mirror's freeze + parent columns; the live read and the two controls; features and states; then Backlog's deletion last, once the tab demonstrably carries everything it did. Deleting first loses capability for however long the rest takes.
  • Does the mirror become the snapshot's source, or stay beside it? This mockup says every screen reads the mirror and the dispatcher keeps reading the live world. The stronger version puts a stale row one bug away from a dispatch. Recommend not, for now.
  • Hierarchy on the history read. listTicketHistory deliberately does not hydrate parents — that read is per-item and a month of backfill would cost a request per ticket. Cheapest honest version: hydrate for the open set only (already fetched for the snapshot), and leave frozen rows with the parent they were last seen with.
  • Freezing on Removed. Azure's Removed means “this was never real”. Same freeze — but should it count in the totals or the spend at all?
  • Cost on a frozen row still moves if a late run is attributed to it. Either the row is not truly frozen, or only the tracker fields freeze and cost is read live. The second is what this draws.
