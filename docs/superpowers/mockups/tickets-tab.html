The four questions, as four links

Both axes and the ordering are fields on Place, so each of these is a URL that survives a reload, steps under Back, and can be pasted to someone else. Defaults are omitted from the query string, which is what keeps “all items” a bare ?tab=tickets rather than a second spelling of the same page.

Show me all unclosed watched items ?tab=tickets&watch=watched&state=open
Show me all closed items ?tab=tickets&state=closed
Show me all unclosed unwatched items ?tab=tickets&watch=unwatched&state=open
Show me all items ?tab=tickets
…and what the finished work cost ?tab=tickets&state=closed&order=cost

The mirror, and the one-month floor

The list is not a live read of the tracker. It is a local table the pulse keeps up to date, and that is what the retention decision makes it: backfill one month, then keep everything forever. Two rules, and they pull in opposite directions, so both are written down rather than left to the reading of whoever implements it.

  • The floor is anchored, not rolling. One month back from the first scan, stamped once and frozen — the same shape as issue_runs.completed_at, and for the same reason. A rolling month would quietly drop the far end of the history every night, which is the exact opposite of what was asked for, and it would do it silently.
  • Nothing is ever deleted. A row the tracker stops returning — closed long ago, moved, untagged, unassigned — stays. The mirror is a record of what was seen, not a copy of what the tracker currently says, which is also why the count in the head reads kept rather than assigned.
  • The floor is stated on the surface, because it is a cap and this codebase does not ship silent ones. “History from 14 Jul 2026” at the head, and the foot of the list says the same thing when you reach it rather than simply stopping.
  • The floor is a floor, not a filter. Backfill pages by last changed, so a ticket filed two years ago that someone touched last week arrives and is then kept like anything else. Worth saying out loud: the history is “everything since the anchor, plus whatever older work is still alive”, and a reader who assumes a clean cut-off will eventually find a 2024 ticket in the list and think the floor is broken.
  • A new table needs no ColumnMigrations entry — but the moment a column is added to it later, it does, guarded by a PRAGMA table_info check (CLAUDE.md, docs/spec/14-persistence.md). Being new once does not keep a table exempt, and the failure is invisible.

What this buys, beyond the retention answer: the counts, both orderings and the paging all become one SQL query over one table, and the tab stops depending on how fast the tracker can be asked for a thousand items.

The one thing that is not a UI change — neither provider can list a closed ticket

The issues seam is open-only on both connectors: listOpenIssues(label?) (src/integrations/github/githubApi.ts) and listOpenWorkItems(tag?, assignedTo?) (src/integrations/azure/azureDevOpsApi.ts), and the GitHub integration's own comment says it fetches every open issue on purpose. Nothing in the harness has ever asked a tracker for a closed item — issue_runs is what remembers them, and it only knows the ones the fleet worked. So “show me all closed items” is a provider change before it is a cockpit change: a new listing method on both *Api interfaces, taking a state, a changed since instant and a page cursor — and, per CLAUDE.md, added to each scripted fake in the same change, or the tests keep passing against a seam that no longer describes the provider.

“Changed since” is the parameter that makes the mirror cheap, and both providers already have it: GitHub's issues list takes since with state=all, and Azure's WIQL can filter on System.ChangedDate. So the backfill is one paged sweep from the anchor, run once, and every pulse after it asks only for what has changed since the last sweep. Without that parameter the tab is a full re-list of the tracker on every pulse, which is the version of this feature that gets turned off.

The assignment filter is also not symmetrical today. Azure has one — filters.workItemAssignedTo, with workItemTag beside it — and GitHub has none for issues: defaultAssignee is documented as “Not a filter: it never narrows what is picked up”, and listOpenIssues() is called with no argument at all. On GitHub this tab would therefore list every issue in the repository. Worth deciding before the route is written: either a GitHub-side assignee filter joins filters, or the tab states which filter it is showing so the list is never silently wider than the phrase “assigned to me” implies.

Ordering

  • Added is the tracker's own id, descending — auto-incremental, so it is the arrival order with no date to parse and no timezone to get wrong.
  • Cost is not the tracker's to know: it is the local store's, and it must come from buildSpendGoals (src/spendInsights.ts) — the one place that decides which goal a run's money belongs to. A second rollup here would be a second opinion about attribution, which is precisely what that module opens by refusing to have.
  • Because the list is a local mirror, both orderings are one query over one table, keyset-paged on (sort key, id) — the id breaking ties so two tickets that cost the same never swap places between pages and hide a row. No per-request ranking, no cache to invalidate, and the question “what has cost the most” is answerable without asking the tracker anything at all.
  • A ticket with no spend sorts last and draws —, not $0.00: never worked and worked for free are different facts, and a zero would state the wrong one.

The two axes are genuinely different readings

  • Watch is the harness's — the ${prefix}-watch / -ignore label pair, resolved by watchBucket. It has three values, not two: an item nobody has opted in is unwatched, and one explicitly tagged leave-alone is ignored. Folding ignored into unwatched would report “nobody has triaged this” about an item somebody deliberately triaged.
  • State is the tracker's — open or closed, its word, not the harness's.
  • The harness's own verdict — delivered, fell short — rides on the row as a chip but is not a third filter, because it answers a different question and would make the control row a cube. It is drawn where it is useful: explaining a closed row that cost a lot.
  • Both readings are quoted from where they already live. Re-deriving the watch bucket from labels here is how two surfaces start disagreeing about what is watched.

Infinite scroll

  • The scrolling container is .cn-sit, so the sentinel at the foot of the list is observed inside it, not against the viewport.
  • Pages of 40, requested one ahead of the foot. The head states loaded of total — an infinite list with no total tells a reader nothing about whether they are near the end.
  • The cursor is a keyset — the last row's sort key and id — not an offset, so a sweep landing mid-scroll cannot shift the window and make a row appear twice or not at all. It carries the filter it was cut from, so changing one starts a new list rather than appending to the old.
  • The foot is a real state, not an absence: reaching it names the floor (“start of history — 14 Jul 2026”). A list that just stops reads as one that failed.
  • Scroll position is deliberately not on Place: a URL that restores a scroll offset into a list that has since grown lands somewhere else entirely. Back returns to the filter, which is the place; the list re-reads its first page.

Where the pieces go

  • Store: a new module under src/store/ owning the mirror table and its frozen backfill anchor — the only directory that touches SQLite, one module per group of related tables, delegated from store.ts under the same method names.
  • Sweep: the pulse writes the mirror through that module. It is a record, not a decision — nothing under src/dispatcher/ reads it, and the tab stays a lens.
  • Route: GET /api/tickets in a new src/server/routes/tickets.ts, wrapped in checked(...), registered in ROUTE_MODULES; query carries watch, state, order, cursor. Fetched, never on /api/state — that endpoint comes round every couple of seconds and this list is all-time.
  • Wire: TicketsPayload in src/wire.ts, shipping its own refUrls off the connector, because buildRefUrls is built from the world and most rows here have left it.
  • Place: 'tickets' joins ConsoleTab and — the site nothing checks — TABS in web/src/cockpit/place.ts, plus the three new fields.
  • Panel: web/src/components/TicketsPanel.tsx, drawing every reference with <Ref> under a nested RefLinks provider that merges the route's URLs over the shell's.
  • Specs, same change: docs/spec/17-cockpit.md (the tab, and its parameters in the address-bar table), docs/spec/16-http-api.md (the route), and — because the seam changes — the provider document that owns the issues integration.

Two states that do not fit in the frames above

The foot of the list, reached

Start of history — 14 Jul 2026, a month before the first scan. Nothing older was ever fetched, and nothing seen since has been dropped.

An infinite list that simply stops reads as one that failed to load. The floor is a cap, so the foot names it.

Still open

  • Does this replace the Backlog tab? It is a superset of it — Backlog is open items grouped by watch bucket, which is this tab with state=open and a grouping. They should probably not both exist for long.
  • Cost of an item that was rolled into another goal (#297 above) reads —, because the money was attributed to the goal that did the work. Correct per buildSpendGoals, but it means a ticket can be closed, real, and free.
  • Is the month configurable? Drawn as a fixed month. It is one number, it is only read once per install, and a knob nobody turns is a knob with a default that has to be right anyway — but it is cheap to expose, and an operator adopting the harness onto a long-running tracker is exactly who would want it wider.
