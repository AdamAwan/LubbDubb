That is all of them — 7 runs, all-time. No pagination: the record is one row per goal the fleet has ever worked, and a fleet that has outgrown one screen of them has outgrown this page's shape, not its page size.

The two open questions the ticket left for planning

What counts as a completed goal, given the verdict tables and the exclusion matrix? Neither a delivery nor any other standing verdict. The row is issue_runs, whose completed_at is stamped the first pulse isGoalComplete holds and is never cleared — so the list cannot lose a goal retroactively when an assessor's shortfall deletes the delivery row it was keyed on (VERDICT_EXCLUSIONS, src/store/verdicts.ts), and it still holds the three goals that finish without a delivery at all: a written retrospective, the agent's own done, and a decomposition whose every part rolled up. A shortfall is therefore listed, not excluded — it is history, and the outcome word says which kind. The predicate is completedAt !== null || dismissedAt !== null, and nothing in the route re-implements isGoalComplete: a second definition of “finished” is how this tab and the dispatcher come to disagree.

Pagination, or all of them? All of them, and the count is stated at the head so the answer is visible rather than assumed. The route is fetched on open rather than polled, so the cost is one read per visit — the argument that already put the work graph on its own route. A limit is the next change, not this one, and it arrives as a Place field so a shared link still names the page someone was on.

The row

  • Outcome first, in a fixed column. Four words — delivered, concluded, fell short, abandoned — folded on the server from resolveIssueConclusion plus the delivery and shortfall rows. The browser renders a word; a second implementation of a precedence rule is a second opinion about it.
  • The title is not a control. A dismissed run is not in the snapshot's issue list, so a goal page keyed on it would render empty. The row names the goal and the reference slot is the way there — which is also why no reference sits inside a button here.
  • The sub-line answers “what was this run” — how long it ran, whether it had a plan, and the assessor's summary or the operator's dismissal note where there is one.
  • The instant is relative, with the absolute one on hover. Newest first, grouped by the day it completed; the grouping is presentation only and holds no state.

References, and the sharp edge under them

  • Three marks, unchanged from the cockpit's vocabulary: a box is a place you can go, a fill means it stays in the cockpit, an arrow means it leaves. A branch keeps the arrow and drops the box.
  • Almost every reference here leaves, and that is correct: a goal this tab remembers left the world long ago, so the tracker is the only destination that exists. The filled tokens above are the two runs still on the floor.
  • The edge: <Ref> resolves against the RefLinks world the shell provides, which holds the snapshot's map — and this route ships its own URLs, resolved off the connector, because buildRefUrls is built from the world these rows have left. A panel that drew <Ref> without merging its map would render every reference as plain text: rows that look right and are dead ends. The fix is a nested provider in refs.tsx that merges over the shell's map and keeps its openGoal/hasGoal.

Where the pieces go

  • Route: GET /api/completed in a new src/server/routes/completed.ts, wrapped in checked(...), registered in ROUTE_MODULES; fetched on open, rate-limited, shipping its own refUrls — the /api/work shape.
  • Wire: CompletedGoalsPayload in src/wire.ts, beside WorkRootsPayload.
  • Place: 'completed' joins ConsoleTab, so TAB_LABEL and tabBody's switch are compile-checked and test/console.test.ts catches the nav — and, the one site nothing checks, TABS in web/src/cockpit/place.ts, without which a shared ?tab=completed silently reads as the overview.
  • Panel: web/src/components/CompletedPanel.tsx.
  • Specs, same change: a tab section in docs/spec/17-cockpit.md stating it is a lens and is fetched rather than polled, its value in the address-bar table, and the route's entry in docs/spec/16-http-api.md.

What is deliberately not here

  • No filter and no search. Either would be state, and state belongs on Place; shipping one in a useState is the bug this ticket names. If a filter is wanted it is a query parameter, like collapsed.
  • No mutation. No un-dismiss, no re-open, no verdict toggle — a history you can edit from is not a history.
  • Nothing about how a goal becomes complete. isGoalComplete, runsToRecord, the verdict matrix and dismissIssueRun are read, none is changed. This is a lens, and no rule under src/dispatcher/ learns about it.
