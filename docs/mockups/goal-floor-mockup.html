Issue #168 · factory skin · third view

The Goal Floor

A ticket arriving, being checked for workability, decomposed into steps, each step producing a pull request, each pull request passing its scanners, the delivered parts filling a silo, and the goal check firing on the lot. One picture, drawn left to right, per goal.

The two graphs the skin has today draw the dispatcher (TheLine) and a plan's prerequisites (TechTree). Neither draws the production line. This is a mockup of the third, with the four open decisions answered below it.

The four decisions

Answered here so the drawing below is a consequence of something, rather than a picture to argue about.

1 · Scope

One floor per goal, picked from a strip of patches.

The per-goal floor is the readable picture and the one the mapping describes. "Is the factory producing" is a rate, and production.ts already answers it numerically — a second, worse answer to that question is not worth a floor.

2 · Source

The snapshot for state, the work graph for existence.

/api/state is the live reading and wins wherever both speak. /api/work/:ref is fetched once when a floor is opened and may only add settled machines the world has forgotten. It never contradicts a live one.

3 · The tech tree

The floor replaces it.

Depth is already how the machines are ordered along the belt, so the tree's one unique claim survives the move. Two views that could disagree about whether a part is done is the outcome the issue rules out — and keeping both is how you get one.

4 · Layout vs reading

Position from structure, state from the poll.

layoutFloor() assigns each machine a (column, lane) from refs and dependency edges alone — column is depth, lane is the branch it sits on — memoised on a structural key. A machine moves only when the graph's shape changes. Tone, word and motion are looked up per render.

01

A stopped machine says why

Every red or amber machine carries a plate underneath it in the machine's own words. The plate is the reason the harness already computed — never prose assembled in the browser.

02

Absent is not stopped

A goal nothing has started on draws a patch and no drill. A goal refused at intake draws a drill that is red and stopped. The two are one glance apart, which is the point of #158 having a verdict at all.

03

Scanners are generated

One scanner per failing check, its state taken from the classification verdict — repair, hold, mute. No check name is ever written in this repository; a config naming a check nobody has heard of draws correctly with no code change.

04

A splitter, where the stream divides

One is drawn at every column where the lane count goes up — after the furnace when a plan's parts are independent, after the first part when they stack on it. It is what makes a single verdict visible at last: one lane straight through, no splitter at all.

05

The belt is the harness

Belts move only while cycles run, exactly as TheLine's does. A belt still running under a paused harness is the one confidently-wrong thing this layout could draw.

Thirteen of the fifteen rows are already on the wire. The two that are not are both verdicts the browser cannot compute without importing server code, which is the one case the issue leaves the door open for.

What the server has to add — and what it must not

Two per-item fields, both computed beside the verdicts that already ride there.

Field Why it cannot be derived in the browser
pr.ciVerdict
{ actionable, dispatch[], escalate[], ignored[] }		 The classification needs the operator's rule set and the glob matcher, both of which live in src/ci/. Shipping the policy instead and re-matching in the browser would be a second implementation of one decision — the drift class this codebase has paid for twice. Computed beside health and attention, from the same call the dispatcher makes.
issue.assay
{ verdict, summary, by, decidedAt }		 pickup.reasons[0] carries the refusal text today, but "refused" and "awaiting a verdict" differ only in that prose. Telling them apart by reading the string is exactly what signalPolarity refuses to do, and for the same reason. Sits beside conclusion and shortfall, never inside pickup.

Nothing else. No new top-level snapshot key, no new route, no dispatcher change, and nothing under web/ importing src/dispatcher/ or src/graph/ — the floor reads the same snapshot every other panel reads, plus one fetch-on-open of the durable graph.

Acceptance, against the drawing

Each line of the issue's list, and where it is satisfied above.

  • Every new noun lands in vocabulary.ts. — machineStatus gains an arm per stage, next to bayMachineStatus and crateMachineStatus, so the floor and the belt keep one answer.
  • A CI machine's state derives from the classification verdict. — floor #212: four scanners, four states, no name written anywhere in the code.
  • A concluded part draws as finished. — floor #204, assembler 2: a determination, in the silo, green, with no PR under it.
  • An unclear assay draws as refused-at-intake, and differently from untouched. — floor #219 against floor #240: a stopped red drill against no drill at all.
  • A shortfall draws as the return path with its route named. — floor #204: the belt runs backwards to the furnace, tagged route · plan.
  • An awaiting_approval plan draws as ghosts, and approving builds the floor. — floor #231: three ghosts, dead belts, and the stamp that fills them in.
  • Parallel work draws as parallel lanes, and never as a converging diamond. — floor #196: a splitter into four lanes, two PRs open at once on one base, a report finishing beside them, a lane held by the cap, and a pollution warning only concurrency can produce.
  • Nothing under web/ imports src/dispatcher/ or src/graph/. — the two verdicts above are why; the structural assertion in workGraph.test.ts gains a sibling for web/.
