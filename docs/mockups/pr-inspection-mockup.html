The ladder, and why it is two groups

variable left, fixed right

siloGates is a fixed four because health.reasons is prose — a numerator with no denominator. That argument holds for three of them and fails for CI, because ciVerdict is an enumerable list: every check the policy classified, by name, with a state. So the ladder splits.

Left · one cell per check

From ciVerdict.dispatch / escalate / ignored plus the passing ones — the same fold goalFloor.ts:scannersFor already does, reused rather than rewritten. The cells share one fixed-width track, so three checks give three fat cells and nine give nine thin ones, and the ladder's total width never changes.

Right · the fixed three

Approved, comments resolved, no conflicts — always the same three columns at the same x, which is what lets you read down the strip. A dotted divider separates them from the scanners, because they are gates a human moves, not checks a machine reports.

Five states, and only one of them is “someone is on it”

damaged is unlit — failing, an agent is coming. not_ours is amber — failing and nobody is coming, which the old single CI cell could not say and which is the entire reason per-check policy exists. muted is a dashed outline, awaiting is blue, passing is green.

Red stays out of the ladder

Every one of those states is amber, blue, green or unlit. Red is left to the court chip and the row stripe, so the floor's rule — red means a question only you can answer — survives a row with four red checks on it.

No provider detail, no scanner group

A provider that reports no ciChecks (and the fake one) leaves the group as a single cell off ciStatus — the pre-policy behaviour, drawn as one wide scanner. Nothing regresses for a project with no ci config.

Names live in the reason, not the ladder

The why column names the check that matters — codeql failing · policy holds it — and the ladder gives the shape. That keeps the row scannable and keeps every check name out of the skin's source, which is the property ScannerState was written to protect.

This needs one server change, and it is a bug either way

prAttention.ts:prConcerns raises the CI concern on pr.ciStatus === 'failing' alone. It never reads ciVerdict. But rule 1 dispatches only when ciVerdict.actionable (ruleDispatcher.ts:284), and rule pr-ci-blocked escalates to a human instead.

So a PR whose only red check is escalated or ignored reports “harness · CI is failing — an agent will be dispatched” today, when no agent is coming and an escalation has been filed for you. That is row #139 above, and it is the exact PR a custom CI policy exists to hand you. The strip would render that verdict faithfully and be confidently wrong — worse than the towers it replaces.

The fix belongs in prConcerns, not in the skin: it should raise the CI concern only when the verdict is actionable, and the you arm should cover a policy-held failure the way it already covers a spent attempt cap. One predicate, server-side, so the strip and the Goal Floor's prReading — which does read the verdict, and already says held — stop disagreeing about the same PR.

Second, smaller: an all-ignored red PR reaches the stalled arm and reports CI has not reported, which is untrue — it reported and you muted it. Worth a reason string of its own while that arm is open.
